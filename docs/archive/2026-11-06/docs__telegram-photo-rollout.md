# Этап C2B: управление фотографиями товара в Telegram-боте — развёртывание, зависимости, риски

Интернет-магазин «Мастер Сварщик». Документ описывает управление
фотографиями товара через бота: просмотр галереи, выбор основного фото,
порядок и обратимое удаление. Все операции — в личном чате сотрудника,
с правом `upload_photos`, двухшаговые (предпросмотр → подтверждение).

## Статус (честно)

- **Реализовано в коде:** просмотр галереи (до 10 фото, без URL и полных
  идентификаторов), основное фото, порядок (выше/ниже), обратимое удаление —
  всё через pending-действия с TTL, anti-replay, аудитом и откатом.
- **Миграция `docs/migrations/0007_bot_photo_actions.sql` НЕ применена.**
  Пока RPC-функций нет, изменения фото безопасно заблокированы сообщением
  «функция ещё не активирована» — ложного подтверждения не бывает.
- **Загрузка новых фото из Telegram: ЗАБЛОКИРОВАНА (fail closed).**
  Флаг `TELEGRAM_PHOTO_UPLOAD_VERIFIED = false` в `src/lib/bot/photos.ts`.
  Бот честно отвечает «Загрузка из Telegram пока не подключена».
- **Живой E2E в Telegram не проводился.**

## Что войдёт в релиз

### Миграция 0007 (по порядку после 0005/0006)

1. Служебные колонки `product_photos` (additive, nullable): `deleted_at`
   (карантин), `mime`, `size_bytes`, `hash` (SHA-256, анти-дубликат),
   `staging_key`, `width`, `height`.
2. Публичная политика чтения: фото в карантине (`deleted_at IS NOT NULL`)
   не видны на витрине. Публичное чтение галереи не требует 0007.
3. `pending_actions.action` расширен: `photo_main`, `photo_reorder`,
   `photo_delete`.
4. RPC (SECURITY DEFINER, REVOKE PUBLIC/anon/authenticated, GRANT только
   `service_role`), все — одна транзакция с блокировками `FOR UPDATE` на
   действие и все фото товара, сверкой before_value, `consumed_at` +
   `outcome='applied'` + аудитом:
   - `bot_set_photo_main` — единственное основное фото; основное всегда
     `sort_order = 0`; прежнее основное остаётся в галерее.
   - `bot_reorder_photo` — двухфазная перенумерация без коллизий; основное
     фото перемещать нельзя (`BOT_PHOTO_MAIN_CANNOT_REORDER`).
   - `bot_delete_photo_meta` — обратимое удаление (карантин, файл в storage
     НЕ удаляется); при удалении основного назначается первое оставшееся;
     последнее фото опубликованного товара удалить нельзя
     (`BOT_PHOTO_LAST_PUBLISHED`); восстановление из карантина — та же
     функция (value-driven, откат приходит со swapped before/after).
   - `bot_prepare_rollback` (обновлён) — фото-действия поддерживаются;
     строгие guards сохранены: только `outcome='applied'` и точное
     совпадение текущего состояния с `after_value`, иначе конфликт.

### Порядок включения

1. Ревизия SQL 0007 (и 0005/0006, если ещё не применены) — глазами.
2. Применение миграций 0005 → 0006 → 0007 инструментом миграций.
3. Перезапуск/перевыпуск backend, чтобы сбросились кэши доступности
   таблиц и колонок (`pendingTableState`, `photoSoftDeleteCol`).
4. Живой E2E в Telegram тестовым сотрудником на тестовом товаре.

## Загрузка новых фото: что нужно для включения (сейчас BLOCKED)

Проверено по документации: Lovable Telegram gateway документирует
скачивание файлов (`getFile` → `GET /file/<path>`). Но это **не проверено
вживую** в этом проекте, и без проверки код-путь включён быть не может.

Для разблокировки:

1. **Живая проверка gateway:** на тестовом боте отправить ботом фото,
   вызвать `getFile` по `file_id` и скачать `/file/<path>`; убедиться, что
   ответ — бинарные данные с корректным `Content-Type` (а не JSON/страница
   авторизации). Только после этого установить
   `TELEGRAM_PHOTO_UPLOAD_VERIFIED = true` в `src/lib/bot/photos.ts`.
2. **Storage:** приватный staging-бакет и отдельный публичный бакет для
   проверенных изображений (UUID-имена файлов). Бакеты НЕ создаются в этом
   этапе — нужны отдельным решением (публичный бакет требует разрешения
   workspace-политики).
3. **Валидация (уже реализована, `src/lib/bot/photos.ts`):** сигнатура
   файла (JPEG/PNG/WebP magic bytes), совпадение заявленного MIME с
   содержимым, размер ≤ 5 МБ, SHA-256 против дублей, проверка URL
   (только https, без внутренних/локальных адресов, без логин-адресов
   Telegram, без учётных данных в URL).

До выполнения пунктов 1–2 добавление фото остаётся честно заблокированным;
интерфейс, валидация и адаптер (`TelegramPhotoFetcher`) готовы.

## Точные оставшиеся риски

- **Gateway-бинарники не проверены** — ключевой риск блокировки загрузки
  (см. выше). Без проверки никакой загрузки не будет.
- **Карантин растёт:** файлы удалённых фото остаются в storage до отдельной
  чистки — это осознанный выбор в пользу обратимости; нужна процедура
  периодической очистки (не входит в 0007).
- **Существующие 1 077 фото** не имеют `hash`/`mime`/размеров — анти-дубликат
  и полная валидация работают только для будущих загрузок.
- **sort_order legacy-данных** может быть неидеальным; первая же операция
  порядка нормализует нумерацию неосновных фото.
- **Откат удаления** восстанавливает `is_main`/`sort_order` из снимка; если
  после удаления появились новые фото, откат получит конфликт (fail closed),
  а не молчаливое переписывание.

## Проверка после включения

- «🖼 Фото» в карточке: список без URL, основное отмечено ⭐.
- Основное: preview → подтверждение → ⭐ переезжает; повторный клик — отказ.
- Порядок: №3 → №2 с подтверждением; основное переместить нельзя.
- Удаление: preview «обратимое, файл в карантине» → фото исчезает из
  галереи; «↩️ Откатить» возвращает; удаление последнего фото витрины — отказ.
- Параллельное изменение галереи другим сотрудником → конфликт.
- Все изменения — в журнале (`photo_main`, `photo_reorder`,
  `photo_quarantine`, `photo_restore`) с actor/time/before/after.

## Откат

- Фото-действия откатываются кнопкой «↩️ Откатить» (preview → confirm).
- Полный откат кода — отключение обработчиков фото; данные и файлы не
  пострадают (удаление и так обратимое).
- Откат миграции 0007: колонки не используются публичным чтением, кроме
  политики карантина; удаление таблиц/колонок — только по прямому решению
  (breaking-миграции запрещены; карантинные фото остаются скрытыми).

## Точечные правила квалификации и первого ответа (24.10.2026)
- Приоритет — первые реально квалифицируемые обращения и учёт лидов. Новые стадии, таблицы и большой проект базы поставщиков не добавляются.
- Граница работы — оборудование/материалы для сварки, резки и смежных работ. Не обещать любую номенклатуру любой отрасли; сомнительное обращение остаётся на ручной проверке, не отклоняется автоматически.
- У владельца почти нет действующих поставщиков. Исторические «Вартекс» и «Сварог» не означают действующий канал; «Вартекс» не отождествляется с VARTEG. В коде нет созданных active suppliers. `supplyStatus=requires_verification` — канал поставки не подтверждён, нельзя обещать результат, наличие или дилерство.
- Первый DRAFT подтверждает получение конкретного обращения (Re: исходная тема, sourceMessageId), благодарит и сообщает, что запрос изучается и проверяется возможность его исполнения с учётом указанных требований. Не предлагает аналогов, не обещает найти любой товар, не заставляет закупщика выбирать технические параметры.
- `questions=[]` в первом черновике: отсутствие извлечённого поля НЕ доказывает отсутствие сведений в оригинале. Сначала человек проверяет письмо и ТЗ, затем спрашивает только объективно недостающие необходимые сведения: например, срок для КП или адрес отгрузки. Обязательность точной марки/допуск эквивалента — только после первого контакта, без прямого предложения аналога в первом письме.
- При любых вложениях `attachmentReviewRequired=true`, предупреждение `attachments_not_parsed`; PDF/XLSX не разбираются, ручная проверка обязательна. Клиента не просят повторить уже предоставленную спецификацию. Сам флаг не означает технически реализованный просмотр вложений: бинарники ещё не принимаются.
- Третий слайд витрины: «Более 1000 товаров в каталоге. Принимаем заявки на FoxWeld, VARTEG, «Сварог» и другие марки.» Это приём заявок, НЕ доказательство наличия товаров «Сварог» в базе или действующего дилерства. База в этом уточнении не проверялась и не изменялась.
- Проверки этого уточнения: 33/33 синтетических B2B-теста, полный набор 288/288; ESLint трёх изменённых TS/TSX-файлов без ошибок, автоматическая сборка `build OK`. Живых обращений и отправок не было.

## API и запуск mock
`POST /api/public/b2b/ingest?dryRun=true`, Authorization: Bearer из будущего секрета B2B_INGEST_TOKEN (минимум 32 символа; добавлять только в Project Settings → Secrets). Без него 503, неверный токен 401. Конкретного токена в репозитории нет. Dry-run по умолчанию, не пишет БД и не вызывает ИИ. `dryRun=false` жёстко заблокирован независимо от токена. Тесты вызывают handler напрямую с синтетическим токеном. Stateless dry-run не имеет долговременного limiter: до публичного подключения требуется ограничение запросов на входном шлюзе; лимит SQL защищает будущие записи, но не расходы LLM (LLM сейчас не вызывается).

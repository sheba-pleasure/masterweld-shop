# Проверка версии при выпуске и откате

Дата: 06.11.2026. В DEV установлено 67b5c91f105c035187e6b59bf6bca808dc56c337. Схема остаётся 0000–0020.

## Исправленная проблема

Прежде release.sh и rollback.sh проверяли HTTP-ответ главной страницы и noindex. После перезагрузки gateway такой ответ мог ещё прийти от прежнего upstream. Он не доказывал, что новый выпуск действительно обслуживает запросы.

Теперь каждый smoke требует ready=true, точный SHA проверяемого выпуска и environment=production. Проверка применяется к новому slot до переключения, к gateway после переключения, к прежнему slot при откате и к gateway после возврата. Если ответ содержит чужой SHA, DEV-среду, неправильный JSON или 503, выпуск не подтверждается. При задержке reload проверка ждёт правильный SHA в рамках ограниченного числа попыток. Невосстановимая ошибка запускает существующий автооткат либо оставляет первый запуск в 503.

Перед переключением уведомления остаются на паузе. Worker активируется только после успешных проверок, как и раньше. Это не обещание повторной идемпотентной доставки Telegram.

## Откуда берётся версия

Docker-сборка записывает GIT_SHA в .output/mw-environment.json. Это тот же аргумент полного SHA, которым уже пользуются git-archive DEV builder и production workflow. Manifest входит в образ; SHA не считывается из параметров HTTP-запроса.

При запуске runtime сверяет RELEASE_SHA с manifest.revision и отвергает отсутствие/несовпадение до подключения к БД. После успешных проверок окружения, маркера базы и включённых Telegram-интеграций runtime устанавливает неизменяемый объект готовности внутри процесса. До этого успешного ответа readiness нет.

SSH-приёмник дополнительно сверяет revision manifest с утверждённым SHA перед потреблением разрешения на выпуск. Docker HEALTHCHECK проверяет readiness SHA/среду и ответ главной страницы.

## Endpoint

GET /api/public/release-health возвращает только:

```json
{"ready":true,"revision":"полный SHA сборки","environment":"dev"}
```

В production значение environment будет production. До подтверждённого standalone startup — 503 с ready=false. Другие методы получают 405. Ответ не содержит токенов, ключей, адреса БД или instance ID; Cache-Control запрещает кеширование, X-Robots-Tag запрещает индексацию. Переданный query expected не выбирает возвращаемую версию.

Это подтверждение проверенного запуска и обслуживающей запрос сборки. Оно не является непрерывной проверкой доступности БД/Telegram и не заменяет проверку каталога, оформления заказа, миграций или прав перед выпуском.

## Совместимость и оставшиеся проверки

Обновлённые production-скрипты допускают только образы с этим manifest и endpoint. Старые образы без них не будут признаны готовыми. В самостоятельном production ещё нет работающего выпуска, поэтому текущий рабочий сайт не затронут. Старый DEV-контейнер сохранён штатным механизмом DEV и может быть восстановлен как контейнер; его старый endpoint не объявляется совместимым с новым production smoke.

Полная репетиция blue/green на настоящих production-подобных контейнерах, автоматический внешний выпуск/откат, домен/HTTPS, перенос данных и переключение ботов остаются отдельными задачами. Этот этап проверил точную версию настоящего DEV и HTTP-механику проверки, но не доказывает завершение всех этих задач.

Main, рабочий gateway, Caddy/VPN/SSH, production-БД и рабочие webhook не менялись. Команда «обнови main» и свежий release review по-прежнему обязательны.

# Независимый магазин — решение владельца 06.11.2026

Lovable используется только для дизайна и разбора интерфейса. Исходники, сборка, данные, бот, домен и выпуск принадлежат самостоятельному проекту на сервере и в GitHub. Отсутствие доступа к редактору Lovable не должно останавливать магазин.

## Что меняется

- Vite настроен напрямую через upstream TanStack Start, Nitro node-server, React и Tailwind. Пакет @lovable.dev/vite-tanstack-config и его зависимости удалены из lockfile.
- Нет клиентского обмена авторизацией с редактором, отправки ошибок в Lovable или резервного Telegram-транспорта через его коннектор.
- Заказы принимаются сервером без аккаунта покупателя. Служебные шаблоны Auth/cron удалены как неиспользуемые; работающий вход покупателя не заявляется.
- Открытый пакет @supabase/supabase-js сохранён как клиент протокола PostgREST. Он работает с нашей PostgreSQL/PostgREST и не требует аккаунта, оплаты или сервера Supabase/Lovable. Имена SUPABASE_* пока сохранены для совместимости конфигурации.
- Проверка ops/check-independence.mjs ищет повторное появление зависимостей Lovable в исходниках, lockfile и сборке; выполняется в Dockerfile и CI. Это статическая проверка известных признаков, а не универсальное доказательство отсутствия любого сетевого обращения.

Прямое подключение Nitro — по [документации TanStack Start](https://tanstack.com/start/latest/docs/framework/react/guide/hosting#nitro) и [Nitro Vite](https://nitro.build/docs/vite); версии зависимостей сохранены.

## Раздельные данные

| Назначение | База/контейнер | Данные |
|---|---|---|
| DEV | masterweld_dev / mw-dev-db | Только учебные |
| Будущий рабочий магазин | masterweld_production / mw-prod-db | Пока пустая схема 0000–0013 |
| Прежний Cloud | Исторический проект Lovable | Сохранён без изменений; перенос ещё не выполнен |

Рабочая база имеет собственные volume mw-prod-pgdata, сети mw-prod-private/mw-prod-edge, JWT, service key и instance_id. Ключ DEV отклоняется рабочим API. База не публикует порт PostgreSQL. API слушает только 127.0.0.1:18084 через mw-prod-api; покупательский сайт пока не подключён.

Команды из корня:
- python3 ops/standalone/data-up.py — создать/возобновить только новый самостоятельный стек. Инициализация разрешена только пустой базе без маркера; существующая маркированная база не мигрируется автоматически. Учебные seed-файлы не используются.
- python3 ops/standalone/backup-check.py — создать копию этой базы, определения ролей без паролей, восстановить в отдельную временную базу того же закрытого PostgreSQL и удалить её после проверки. Файлы копии остаются в ops/.state/production/backups.
- node ops/check-independence.mjs --built — проверить исходники и готовую .output.

Секреты: ops/.secrets/production, каталог 700, файлы 600. database.env содержит только настройки базы; build-public.env — публичную конфигурацию сборки. Это не готовый shop.env: рабочий бот ещё не создан. При подготовке shop.env нужно перенести эти production-значения и добавить отдельный проверенный бот, сохранив защитные проверки запуска. Не копировать DEV env. JWT создаются на год; ротацию провести до истечения срока с пересборкой публичного ключа и согласованным переключением сервера.

В шаблоне выпуска приложение подключается к mw-prod-edge, gateway направляет /backend/rest/v1/ на локальный API. Эти изменения ещё не означают выпуск: main не обновлён, публичный gateway продолжает отдавать 503.

## Проверенное резервирование и границы

06.11.2026 восстановлена копия пустой самостоятельной базы 20261106T051201Z-43b20f12.dump; products/orders/staff/submissions/notifications — по нулю. Проверены закрытый прямой INSERT и наличие RPC попыток. Это доказательство восстановления новой схемы, а не переноса Cloud, резервирования фотографий или аварийного восстановления после потери всего сервера.

До покупателей нужны перенос и сверка нужных данных из прежнего Cloud в самостоятельную базу, перенос зависимых файлов на собственное хранение, внешняя резервная копия и проверка восстановления на чистом сервере. Старый Cloud нельзя удалять или отключать до завершения сверки. Существующие 1038 товаров, 2 заказа и 4 записи staff не считаются автоматически актуальными: сохранить исходный экспорт и явно сверить назначения/права. Реальные данные не загружать в публичный DEV.

Прежний PRODUCTION-MIGRATION-PLAN.md описывает ревизию Cloud и исторический вариант обновления его на месте. По новому решению целевой вариант — экспорт и перенос в собственную базу, без миграций исходного Cloud.

## Польза Lovable для дизайна

Получен разбор компонентов без запроса на изменение приложения. Lovable прочитал свою копию исходников; полноценный просмотр экранов им не подтверждён. Его рекомендации сверяются с актуальным DEV.

Приняты:
- После добавления товара видно количество и действие «Перейти в корзину».
- В корзине постоянные подписи полей и объяснение неактивной кнопки.
- Убраны кнопки неподключённой оплаты/доставки и неработающего кабинета.
- Пустая корзина ведёт в каталог; телефон берётся из общего CONTACTS.
- Галерея прокручивается на телефоне, миниатюры подписаны для доступности.
- Убрано неподтверждённое обещание доставки из описания товара; ошибки/404 переведены на русский.

Не принят совет безусловно писать «Заказ не отправлен» при сетевой ошибке: результат может быть неизвестен после успешной записи. Сохранена проверка исходной попытки без нового заказа.

Дальше Lovable полезен для вариантов карточек, каталога/фильтров, адаптивных макетов и состояний форм. В него не передаются токены и реальные данные покупателей. Изменения переносятся вручную в ветку DEV и проверяются. План редактора не даёт разрешения менять backend, базы, подключать сервисы или обновлять main.

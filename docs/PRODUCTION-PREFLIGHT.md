Состояние на 07.11.2026 (МСК). Эти инструменты подготавливают и проверяют; они не обновляют main, не переключают ботов и не разрешают выпуск.

Preflight перечисляет файлы drizzle/migrations и docs/migrations и дополнительно два явно указанных обязательных предложения 0042/0043 с закреплёнными SHA-256. Проверяется журнал schema_files по точному пути и хешу; это не доказательство фактической установки функций и не разрешение запуска. Совместимость полного словаря проверяется отдельным app_compatibility. Репетиция схемы 0013 → 0031 → 0043 на вымышленных данных прошла без копирования рабочих баз: [проверки и ограничения](PRODUCTION-SCHEMA-0043.md). Сам рабочий переход, применимость к фактическим данным и оператор продолжения остаются открытыми. Репетиции до 0031 на production/Cloud-копиях: [текущий отчёт и ограничения](OFFLINE-0031-VERIFICATION.md). Проверка:
- Сверяет формат/назначение обоих токенов и полей окружения, разделение секретов между средами и ролями.
- Выполняет только Telegram getMe и getWebhookInfo. Не читает сообщения, не вызывает getUpdates/setWebhook/deleteWebhook и не отправляет сообщений. Точный старый URL и сообщения ошибок провайдера не печатаются. Методы чтения описаны в [Telegram Bot API](https://core.telegram.org/bots/api#getwebhookinfo).
- Проверяет маркер рабочей базы через фиксированный loopback API 127.0.0.1:18084. Docker-имя mw-prod-api в runtime не подменяется: host-проверка использует опубликованный локальный порт и сверяет instance ID.
- Читает журнал файлов миграций только из mw-prod-db после проверки метки контейнера и идентичности базы. Показывает отсутствующие, неожиданные или изменённые SQL-файлы по SHA256. Требуемые предложения 0042/0043 перечислены явно, их байты сверяются с закреплёнными контрольными суммами до сравнения журнала. Не исполняет SQL из файлов и не добавляет записи журнала.
- Проверяет разрешение DNS shop.masterweld.ru. Успешный DNS сам по себе не доказывает маршрутизацию, HTTPS или работоспособность сайта.

## Историческая репетиция на копии

Ниже описан ранее проверенный механизм. Сейчас его не запускать: он создаёт новые копии, а владелец остановил эту работу.

`python3 ops/standalone/rehearse-upgrade.py` предназначен только для нынешней **пустой** standalone production-БД с известным журналом 0000–0013. При появлении любых данных в public или расхождении журнала он останавливается до копирования. Это не универсальная команда миграции.

Он сохраняет pg_dump и определения ролей без паролей в закрытом каталоге ops/.state/production/rehearsals, восстанавливает их в новом PostgreSQL 17.6 с --network none, сравнивает отпечатки всех public/mw_private таблиц, применяет явный диапазон 0014–0028 только в копии и проверяет:
- сохранение прежних данных и instance ID;
- полный журнал миграций с контрольными суммами;
- запрет прямого INSERT заказов для anon/service_role и публичного вызова служебной RPC;
- первое принятие Telegram-события и отказ повтору, включая перезапуск;
- неизменность исходной базы;
- 48 семейств/40 определений/69 привязок/14 единиц без автоматического заполнения товаров;
- закрытые технические таблицы и RPC; единственное разрешённое публичное SECURITY DEFINER-чтение — public_product_technical(uuid);
- отказ synthetic-источникам вне DEV; применение, повтор и откат редактора на транзакционных фикстурах с полным ROLLBACK;
- оба включённых триггера защиты диалогов и отсутствие прямого доступа к их функции;
- отказ второму диалогу в обоих направлениях с сохранением первого; после отмены ввод доступен;
- закрытость bot_draft_results, доступность атомарного RPC и запрет прежнего обходного RPC;
- повтор результата создания без изменения нового ввода, сохранение отмены, один товар/аудит и два результата для двух проверочных попыток; все фикстуры откатываются;
- закрытость bot_editor_previews, восстановление прежнего предпросмотра с сохранением нового ввода;
- read результата без изменения pending/аудита, единый итог apply/cancel, закрытость пяти старых RPC;
- удаление временного контейнера и его volume.

Временный кластер не имеет опубликованных портов, приложения или рабочих ботов. Случайные имена исключают перезапись существующих ресурсов.

## Что ещё необходимо до запуска

1. Перед рабочим переносом сверить возраст имеющегося снимка и изменения исходного каталога, ассортимент, повторные SKU и исключения. Исторический снимок не доказывает актуальность сегодняшних данных. Новых снимков сейчас не создавать; реальные данные не отправлять в публичный DEV. Получение исходных фотографий остаётся открытым.
2. Яндекс.Диск выбран; историческая прикладная копия загружена и восстановлена после скачивания. Действующее расписание DEV сохраняется без изменений. Отдельную работу над резервированием владелец остановил: не создавать новые копии, выгрузки или расписания и не повторять восстановление с созданием новых архивов. При будущем release review оценить возраст и ограничения уже имеющихся доказательств. История: [DATABASE-BACKUPS.md](DATABASE-BACKUPS.md), [BACKUP-YANDEX.md](BACKUP-YANDEX.md).
3. Проверить доказательства миграций на окончательном наборе данных; применить их в собственной рабочей базе в согласованном порядке.
4. Настроить рабочий домен/HTTPS, провести испытание настоящего выпуска и отката, проверить и включить подготовленные рабочие уведомления.
5. Проверить рабочий вход и права семи продавцов по переданным владельцем ID. Они уже подключены только в DEV; соответствие имён ID пока неизвестно. Закупочные цены продавцам доступны по решению владельца, импорт и изменение цен — нет.
6. После «обнови main» повторить весь release review для конкретной версии. Только затем активировать конфигурацию и переключать оба webhook без удаления ожидающих событий. Наличие candidate или зелёного CI этого не разрешает.

Подготовленность конфигурации, готовность базы, публикация сайта и подключение ботов — разные состояния. Диагностика показывает их отдельно.

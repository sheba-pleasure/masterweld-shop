# Проверка будущего рабочего запуска

Состояние на 06.11.2026. Эти инструменты подготавливают и проверяют; они не обновляют main, не переключают ботов и не разрешают выпуск.

После подключения пошагового редактора DEV находится на 0020; самостоятельная production-БД остаётся на 0013. Перед рабочим выпуском нужны проверка и отдельное применение всего диапазона 0014–0020. Новая закрытая репетиция подтверждает диапазон до 0020 на нынешней пустой базе и на архивной копии Cloud. Это не применение миграций к рабочей базе и не разрешение выпуска.

## Подготовленная конфигурация

`python3 ops/production/stage_config.py` собирает существующие защищённые database.env и bots.env в `ops/.secrets/production/shop.env.candidate`. Файл 0600, вне Git. Проверяются разделение с DEV, разные служебный/покупательский боты и webhook-секреты, ожидаемые ID ботов, самостоятельная база и соответствие публичным настройкам сборки.

Повторный запуск с теми же параметрами ничего не меняет. Отличающийся существующий candidate не перезаписывается. Неизвестные ключи, повторные ключи, небезопасные права и символические ссылки отвергаются. Файл `ops/.secrets/shop.env`, который читает выпуск, не создаётся. Копирование candidate в активную конфигурацию не является разрешённым следующим действием до свежего release review.

Подготовлены @masterweldermanagerbot для сотрудников и @msvarbot для покупателей. Уведомления production пока выключены. Подготовленный worker проверяет рабочего служебного бота, webhook и разрешение активному slot/SHA; release/rollback управляют этим разрешением. Для включения всё ещё нужны рабочий выпуск, переход webhook, проверенные получатели и отдельная приёмка: [ORDER-NOTIFICATIONS.md](ORDER-NOTIFICATIONS.md).

## Проверка без изменений

`python3 ops/production/preflight.py --staged` проверяет candidate. Без --staged проверяет активный shop.env; сейчас его отсутствие ожидаемо.

Проверка:
- Сверяет формат/назначение обоих токенов и полей окружения, разделение секретов между средами и ролями.
- Выполняет только Telegram getMe и getWebhookInfo. Не читает сообщения, не вызывает getUpdates/setWebhook/deleteWebhook и не отправляет сообщений. Точный старый URL и сообщения ошибок провайдера не печатаются. Методы чтения описаны в [Telegram Bot API](https://core.telegram.org/bots/api#getwebhookinfo).
- Проверяет маркер рабочей базы через фиксированный loopback API 127.0.0.1:18084. Docker-имя mw-prod-api в runtime не подменяется: host-проверка использует опубликованный локальный порт и сверяет instance ID.
- Читает журнал файлов миграций только из mw-prod-db после проверки метки контейнера и идентичности базы. Показывает отсутствующие, неожиданные или изменённые SQL-файлы по SHA256.
- Проверяет разрешение DNS shop.masterweld.ru. Успешный DNS сам по себе не доказывает маршрутизацию, HTTPS или работоспособность сайта.

Код завершения 1 и approved=false означают «выпуск не разрешён». Инструмент никогда не создаёт разрешение. Автоматические результаты не заменяют ручную проверку перечисленных доказательств.

Проверка 06.11 подтвердила разные параметры DEV/production, оба ID Telegram и маркер production-БД. Pending updates = 0, ошибок доставки в полученных ответах нет. Служебный бот сохраняет прежний webhook, покупательский webhook отсутствует. DNS shop.masterweld.ru не разрешился. Повторный preflight после новой репетиции подтвердил: production ещё 0000–0013, не хватает 0014–0020; DNS shop.masterweld.ru не разрешается, webhook не переключены, candidate не активирован. approved=false; репетиция сама не разрешает выпуск.

## Репетиция на копии

`python3 ops/standalone/rehearse-upgrade.py` предназначен только для нынешней **пустой** standalone production-БД с известным журналом 0000–0013. При появлении любых данных в public или расхождении журнала он останавливается до копирования. Это не универсальная команда миграции.

Он сохраняет pg_dump и определения ролей без паролей в закрытом каталоге ops/.state/production/rehearsals, восстанавливает их в новом PostgreSQL 17.6 с --network none, сравнивает отпечатки всех public/mw_private таблиц, применяет явный диапазон 0014–0020 только в копии и проверяет:
- сохранение прежних данных и instance ID;
- полный журнал миграций с контрольными суммами;
- запрет прямого INSERT заказов для anon/service_role и публичного вызова служебной RPC;
- первое принятие Telegram-события и отказ повтору, включая перезапуск;
- неизменность исходной базы;
- 48 семейств/40 определений/69 привязок/14 единиц без автоматического заполнения товаров;
- закрытые технические таблицы и RPC; единственное разрешённое публичное SECURITY DEFINER-чтение — public_product_technical(uuid);
- отказ synthetic-источникам вне DEV; применение, повтор и откат редактора на транзакционных фикстурах с полным ROLLBACK;
- удаление временного контейнера и его volume.

Временный кластер не имеет опубликованных портов, приложения или рабочих ботов. Случайные имена исключают перезапись существующих ресурсов.

Исходники: `d480855f3ff94b9a5f318bcc01f141f86365c47b`, чистое дерево. SHA256 общей SQL-проверки: `98d28c5e680511858d6a3ead72d915ed4964c94270cb320175f7b9b305640041`. Report содержит хеши миграций и скрипта; источник сохранил прежние отпечатки и схему 0013. Прежний отчёт 20261106T074145Z-878cf0bf подтверждает только диапазон до 0016 и сохранён отдельно.

Это восстановление отдельного кластера на том же сервере. Оно не доказывает восстановление после потери сервера, полноту Cloud-экспорта или сохранность реальных фотографий. На исходной production-БД миграции не применялись.

## Что ещё необходимо до запуска

1. Экспортировать Cloud и файлы, проверить восстановление и сопоставить ассортимент/повторные SKU/исключения. Реальные данные не отправлять в публичный DEV.
2. Выбрать место внешней резервной копии и испытать восстановление вне этого сервера.
3. Проверить доказательства миграций на окончательном наборе данных; применить их в собственной рабочей базе в согласованном порядке.
4. Настроить рабочий домен/HTTPS, провести испытание настоящего выпуска и отката, проверить и включить подготовленные рабочие уведомления.
5. Сверить роли владельца, Валентины и Светланы по реальным ID; пока продавцы их не передали.
6. После «обнови main» повторить весь release review для конкретной версии. Только затем активировать конфигурацию и переключать оба webhook без удаления ожидающих событий. Наличие candidate или зелёного CI этого не разрешает.

Подготовленность конфигурации, готовность базы, публикация сайта и подключение ботов — разные состояния. Диагностика показывает их отдельно.

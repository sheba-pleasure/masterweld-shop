# План миграции пустой рабочей базы

Подготовлен 07.11.2026. Это инструмент чтения, подготовки SQL и проверки квитанции. Он не выполняет миграции, не переключает приложение и не разрешает выпуск. Main, действующий DEV, рабочие боты и резервирование не изменены.

## Назначение и границы

Самостоятельная PRO-база сейчас имеет схему 0000–0013. Новое приложение требует 0000–0043. Построитель ops/production/migration_plan.py подготавливает переход только для пустой самостоятельной базы; перенос каталога идёт отдельным этапом после её подготовки.

Настоящая проверка только чтением подтвердила: 21 публичная таблица, суммарно ноль строк, 14 точных записей журнала, квитанции этого оператора отсутствуют. Это не проверка исходного каталога Lovable и не применение миграций.

Отпечаток структуры связывает план с конкретной базой: учитывает определения, права, роли, политики, триггеры, индексы и другие перечисленные в коде метаданные. Он включает OID и не переносится на другую восстановленную базу. Физические счётчики PostgreSQL, содержимое бизнес-строк и пароли в него не входят. Отпечаток обнаруживает изменение после инспекции, но сам по себе не доказывает правильность исходной схемы. До рабочего применения нужны отдельная ревизия фактической схемы и окно без параллельных административных DDL.

## Три действия

Команды выполняются разработчиком из корня проекта. Пути выходных файлов нужно выбрать заранее в закрытом каталоге ops/.state. Файлы создаются с правами 0600 без перезаписи. Секреты не требуются и в результат не включаются.

1. inspect --output ПУТЬ читает только фиксированную mw-prod-db / masterweld_production. Проверяет метку контейнера, его запуск и маркер production; DEV отвергается. Транзакция REPEATABLE READ READ ONLY возвращает количества, журнал, отпечаток структуры и имеющиеся квитанции.
2. plan --inspection ПУТЬ --output ПУТЬ работает локально. Требует чистого Git-коммита и сохраняет JSON с манифестом, контрольной суммой и SQL. План связан с UUID операции, instance ID, исходной схемой, точным SHA кода и контрольными суммами всех 44 миграций. Файл содержит SQL, поэтому его нельзя передавать непроверенному исполнителю.
3. status --plan ПУТЬ читает фактическую базу и сверяет результат с планом. Проверяет неизменность самого плана и его исходников. Команды apply в инструменте нет.

Все три подкоманды запускаются через python3 ops/production/migration_plan.py. На этом этапе автоматического рабочего исполнителя нет.

## Что делает подготовленный SQL

Одна транзакция берёт advisory lock и блокировки существующих таблиц, повторно проверяет точную базу, исходный журнал, метаданные, отсутствие прежней квитанции и любых бизнес-строк. Изменившееся состояние останавливает установку до миграций.

В транзакции применяются только 0014–0043 и соответствующие записи журнала. 0042/0043 явно перечислены и закреплены хешами; произвольные черновики не подхватываются. После миграций сравниваются все строки четырёх технических справочников, журнал и отсутствие неожиданно созданных бизнес-данных. Проверяются закрытый публичный доступ к закупочным ценам, запрет прямой вставки заказов и закрытые внутренние функции.

В той же транзакции создаётся закрытая квитанция с UUID операции, SHA исходников, хешем манифеста, исходным и конечным отпечатками. Ошибка до COMMIT откатывает схему, журнал и квитанцию вместе. Повтор установки отвергается.

## Если ответ потерялся

- committed: совпали квитанция операции, контрольные суммы, журнал и текущий отпечаток структуры. Это подтверждает зафиксированный переход, но не готовность магазина принимать покупателей и не неизменность всех будущих данных.
- baseline_unchanged: видна прежняя пустая база без квитанции. Это не разрешение повторить SQL: предыдущая команда может ещё работать. Сначала установить состояние прежнего процесса и соединения.
- review_required: состояние расходится с планом или квитанцией. Нужна проверка разработчика; автоматического повтора нет.
- Ошибка чтения также не означает, что COMMIT не состоялся. Не запускать установку заново по таймауту наблюдения.

При будущей смене исходников проверять старый план его точным коммитом. Если изменились относящиеся к плану исходники, проверка остановится. Для нового выпуска потребуется свежая инспекция и план точного согласованного SHA.

## Проверки

58 production unit-тестов прошли. Отдельный сценарий python3 ops/tests/production-migration-plan.py создаёт PostgreSQL только из исходников и вымышленных данных: сеть none, без портов, рабочих томов, конфигурации и резервных копий.

Проверены неверная идентичность, изменение структуры и прав, испорченный журнал, появление раздела, ошибка непосредственно перед COMMIT, успешная установка, чтение квитанции после намеренно отброшенного ответа, отказ повтору, перезапуск, позднее изменение схемы и приватность квитанции. После каждого отказа сверяются прежняя структура и данные. После успешного перехода отдельно запускается общий production guard и полное сравнение словаря. Временный контейнер и том удалены. Сценарий включён в обязательный CI.

Это проверка PostgreSQL и алгоритма восстановления результата. Она не моделирует все сетевые отказы реального сервера, не переносит настоящий каталог и не проверяет Telegram на телефоне.

## Что остаётся до рабочего перехода

После отдельного «Обнови main» нужна свежая проверка выпуска: реальная схема, точный SHA и CI, согласованный ассортимент/данные, рабочий адрес, отключение прежних писателей, совместимое приложение и порядок переключения/отката. Команда владельца не отменяет выявленные блокеры.

Подготовленный файл не применять сейчас. Рабочая база остаётся 0013. Новые резервные копии, загрузки и расписания не создавать по указанию владельца.

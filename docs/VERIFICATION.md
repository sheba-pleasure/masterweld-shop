## Общая попытка оформления между вкладками

Подготовлено, ещё не установлено в DEV. Воспроизведён дефект: две настоящие вкладки одновременно отправляли идентичные данные с разными requestId. Новая reservation в IndexedDB связывает точный fingerprint серверного payload с одним ID. Конкурирующие readwrite-транзакции получают один ID; ответ выдаётся вызывающему коду только после commit транзакции. [Основание: порядок транзакций IndexedDB](https://www.w3.org/TR/IndexedDB/#transaction-scheduling).

Хранятся только fingerprint и requestId, без имени, телефона и содержимого заказа. Подтверждённая запись не удаляется по таймеру. После окончательного отказа удаляется только запись того же ID. Неизвестный ответ не освобождает попытку. Старая подтверждённая команда повторения не создаёт третий ID при гонке с другой вкладкой. Конфликт старой sessionStorage с новым ID останавливает отправку.

Оформление использует общий ID до первого серверного вызова. Повторное получение принятого заказа объясняется на экране; оставшиеся товары сохраняются. Для ещё одного идентичного заказа нужны «Нужен ещё один заказ — проверить корзину» и отдельное оформление после проверки. Закрытие окна отменяет это подтверждение. Кнопка блокируется до асинхронного сохранения ID; ошибка хранилища не разрешает отправку с запасным новым номером.

**1228 Vitest / 68 файлов**, TypeScript, ESLint и Prettier прошли. В компонентных тестах IndexedDB/сервер заменены тестовыми функциями. Отдельный настоящий Chromium проверил сам IndexedDB: 32 параллельных reservation из двух вкладок дали один ID, 32 конкурирующих подтверждения повторения — один новый ID. Проверены перезагрузка, конфликт старого resume, защита новой записи от старого отказа, abort записи и отсутствие персональных полей в сохранённых записях.

Полный интерфейс с настоящей IndexedDB и подменённым сервером: две параллельные отправки получили один ID; следующий идентичный ввод проверил этот же ID; только явное подтверждение повторения создало новый.

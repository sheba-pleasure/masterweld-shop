# Развёртывание редактора карточек в Telegram-боте (этап C2A)

Интернет-магазин «Мастер Сварщик». Редактор отдельных карточек товара:
текстовые поля, перенос в раздел, статус/публикация, создание черновика,
откат. Все изменяющие операции — двухшаговые (предпросмотр → подтверждение),
атомарные, с аудитом; выполняются только в личном чате сотрудника.

## Статус

- Код и тесты готовы (148 тестов), сборка проходит.
- **Миграции 0005 и 0006 НЕ применены** к базе. Пока RPC-функций нет,
  любые изменения безопасно заблокированы сообщением «функция ещё не
  активирована» — частичных записей не бывает.
- Реальный E2E в Telegram не проводился.

## Что войдёт в релиз

### Миграции (по порядку, только после ревизии)

1. `docs/migrations/0005_bot_pending_actions.sql` — таблица pending_actions
   (C1: preview→confirm, TTL 15 мин, consumed_at, before/after). Только
   service_role, без публичных политик.
2. `docs/migrations/0006_bot_catalog_editor.sql` — этап C2A:
   - расширяет CHECK `pending_actions.action` (price, stock, title,
     description, specs, brand, sku, category, status) — данные не меняются;
   - таблица `bot_editor_states` — состояния диалогов редактора
     (одно на сотрудника, TTL 15 мин, consumed_at); service_role only;
   - RPC (только service_role):
     - `bot_apply_pending(uuid, bigint)` — одна транзакция: блокировка
       строки действия и товара (`FOR UPDATE`), проверка владельца/TTL/
       consumed, строгая проверка after_value НА УРОВНЕ БД (цена > 0 и
       ≤ 10 000 000, не более 2 знаков после запятой; статус только
       draft/published/hidden; наличие — boolean; иначе транзакция
       откатывается целиком — «ложного изменения» не бывает), сверка
       before_value, UPDATE товара, `consumed_at = now()` +
       `outcome = 'applied'`, запись в staff_audit_log
       (actor/time/before/after). Для статуса `published` дополнительно
       проверяются обязательные поля (название, цена > 0, хотя бы одно
       фото) прямо в базе.
     - `bot_cancel_pending(uuid, bigint)` — атомарная отмена,
       `outcome = 'canceled'`; отмена НИКОГДА не считается применением.
     - `bot_prepare_rollback(uuid, bigint)` — создаёт НОВОЕ pending-действие
       с обратными значениями (откат тоже через предпросмотр и
       подтверждение) и ТОЛЬКО если: `outcome = 'applied'` (legacy-строки
       без outcome — fail closed) И текущее значение ТОЧНО равно
       `after_value` исходного действия; иначе `BOT_ROLLBACK_CONFLICT` и
       pending rollback не создаётся.
     - `bot_create_draft(bigint, text, text, numeric)` — создаёт товар
       только в статусе `draft`; дублирующийся SKU — отказ (случайная
       позиция не выбирается); slug генерируется из названия
       (`bot_slugify`) с суффиксом уникальности; `source_url` не
       приписывается; ID — UUID.

Применение — через инструмент миграций Lovable (файлы в docs/ — материал
для ревизии, автозапуска нет).

### Порядок включения

1. Ревизия SQL (0005, затем 0006) — глазами, с проверкой RPC и GRANT/REVOKE.
2. Применение миграций 0005 → 0006 инструментом миграций.
3. После применения перезапустить/перевыпустить backend, чтобы кэш
   доступности таблиц (`pendingTableState`, `editorTableState`) сбросился.
4. Живой E2E в Telegram — тестовым сотрудником, на тестовом товаре
   (например, черновике): /price, /stock, /set title, /set cat, /set status,
   /new, откат через «↩️ Откатить».

## Роли и права (private chat обязателен)

| Действие | Право | seller | director (простой) | director (полный) | admin |
|---|---|---|---|---|---|
| Текст: название/описание/характеристики/бренд/артикул | edit_products | да | — | да | да |
| Цена | edit_prices | — | да | да | да |
| Пометка наличия | edit_stock | да | да | да | да |
| Перенос в раздел | manage_categories | — | — | да | да |
| Статус/публикация | publish_products | — | — | да | да |
| Создание черновика | edit_products | да | — | да | да |
| Закупочные цены | view_costs | — | да | да | да |

Права продавца молча не расширяются: перенос и публикация для seller
недоступны. Закупочные цены (product_costs) в редакторе не читаются и
не изменяются.

## Проверка после включения

- Предпросмотр показывает «было → станет»; без подтверждения ничего не
  меняется; повторное подтверждение отклоняется («уже выполнено»).
- Параллельное изменение: если другой сотрудник уже поменял значение,
  подтверждение отклоняется («данные изменились»).
- Публикация карточки без цены/фото/названия — отказ с перечнем недостающего.
- Дубль SKU при /set sku или /new — отказ.
- Все изменения видны в staff_audit_log (actor/time/before/after).

## Откат (строгие правила)

- Каждое применённое действие откатывается кнопкой «↩️ Откатить»:
  новое pending-действие с обратными значениями, снова предпросмотр и
  подтверждение. Неограниченного редактирования БД нет.
- **Откат разрешён только для `outcome = 'applied'`.** `consumed_at`
  выставляется и при отмене, поэтому отменённое действие откатить нельзя.
- **Конфликт значений:** если после применения поле изменили ещё раз
  (100→200→300), откат исходного 100→200 запрещён — текущее значение
  должно ТОЧНО равняться `after_value` исходного действия. Иначе
  `BOT_ROLLBACK_CONFLICT`, pending rollback не создаётся. Молчаливого
  «вернуть как было» не бывает.
- **Legacy-строки без `outcome`** (созданные до миграции) не откатываются:
  доказательства применения нет — fail closed.
- Право на откат проверяется в коде ДО вызова RPC (по типу исходного
  действия); RPC дополнительно проверяет владельца.
- Полный откат кода — отключение команд в боте; данные, созданные
  черновиками, удаляются вручную только по отдельному решению.

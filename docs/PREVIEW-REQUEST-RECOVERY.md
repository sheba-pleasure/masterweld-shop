# Восстановление прямого предпросмотра и подготовки отката

## Сценарий сотрудника

Команды /set, /price, /stock и кнопки статуса/фотографий сначала сохраняют предпросмотр. Подтверждение — отдельный шаг. Если ответ потерялся, кнопка «Проверить предпросмотр» читает прежний результат. «Мои правки» в меню, постоянной клавиатуре и /actions позволяет найти запись даже при потере самого сообщения Telegram.

Повтор той же доставки команды или той же кнопки возвращает первый сохранённый предпросмотр: значения, срок и итог не заменяются. После отмены или истечения срока этот запрос не создаётся заново. Для новой правки нужна новая команда либо новая карточка/кнопка. Подготовка отката привязана к исходному применённому действию, поэтому повтор «Откатить» из разных сообщений не создаёт ещё один обратный предпросмотр. Отменённый откат повторно не подготавливается; при необходимости следует сделать новую правку текущего значения.

Чтение и список не применяют изменения. При недоступности базы бот сообщает о неопределённом результате, а не утверждает, что запись отсутствует. Переходы в меню и список не потребляют незавершённый ввод. Каждая запись списка показывает тип правки, товар, состояние и московское время; подробные сохранённые значения открываются отдельно. Список ограничен десятью записями на странице, от новых к прежним.

## Реализация и ограничения

0025 добавляет закрытую таблицу bot_pending_requests. RPC bot_pending_preview блокирует действующего сотрудника и сохраняет pending вместе с квитанцией в одной транзакции. Для отката в ту же транзакцию входит прежняя проверка состояния товара и аудит подготовки. Первый результат возвращается раньше новой подготовки; фактический исход и права повторно проверяет 0024 bot_pending_operation.

Ключ включает ID бота, сотрудника и исходного сообщения/кнопки. Для отката используется ID исходного действия. Токены в ключ не входят. Перед повторным чтением каталога обработчик ищет сохранённый результат, поэтому повтор не подменяется текущими значениями или иным индексом фотографий. Новая команда является новым намерением; она не объединяется с другими командами по похожему тексту.

bot_pending_history возвращает только собственные записи и только доступные текущей роли типы действий. Закупочные цены, чужие операции и содержание личных заказов не входят. Прямые INSERT/UPDATE/DELETE pending_actions для service_role и старый RPC bot_prepare_rollback закрываются. Старое приложение после 0025 не сможет безопасно готовить прямые правки/откат; при возврате старого образа нельзя восстанавливать обходные права.

Состояния применённого результата, отмены, истечения и старого неопределённого исхода наследуются из 0024. Квитанции не подменяют исторический аудит. Физическое удаление связанных pending запрещено внешними ключами; очистку нельзя выполнять без отдельной политики хранения.

## Проверка DEV

- 799 Vitest / 43 файла на основной реализации; строгий typecheck и ESLint изменённых TS прошли. После правки подтверждения callback повторно прошли 19 профильных тестов, typecheck и ESLint, затем Docker-сборка.
- Отдельный PostgreSQL без сети: восемь одновременных запросов дают один pending; повтор отката — одну запись аудита. Ошибка вставки квитанции откатывает pending и аудит. Проверены текущие роли всех типов действий, чужой владелец, закрытые старые записи/RPC, пустое чтение без создания, пагинация, отмена/истечение, dump/restore/restart.
- ops/dev/verify-preview-requests.ts выполнил сценарий с настоящей DEV-БД по HTTPS и Telegram владельца: потеря ответа после COMMIT прямого предпросмотра и подготовки отката, перезапуск приложения, повтор команды/кнопки, поиск в истории и отмена двух учебных предпросмотров без применения товара. Исходное применённое действие, товары, заказы, уведомления, характеристики и обычный ввод сохранились. Входящие команды и callback acknowledgement симулируются; Browser Skill и визуальная проверка не выполнялись.

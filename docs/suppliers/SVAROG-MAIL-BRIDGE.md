## Что делает мост

1. Сверяет фактический Gmail profile с `bkush7430@gmail.com` до чтения сообщений.
2. Ищет только письма доменов `svarog-spb.ru`, `svarog-rf.ru` и релевантные сообщения от `info@masterweld.ru`. Spam/Trash исключены. Начальная дата `--since` задаётся как календарная дата в UTC; для Gmail используется Unix timestamp.
3. Получает полный оригинал `format=raw`, сохраняет точные байты EML и SHA-256. Чтение не ставит отметку прочтения.
4. Сохраняет вложения по SHA-256, исходное имя, MIME, индекс и связь с конкретным оригиналом.
5. Для безопасно названного XLSX соответствующего MIME вызывает `svarog_price_updates.intake()`. Снимок, сравнение и отчёт остаются частными, непроверенными человеком.
6. Записывает неизменяемую квитанцию. Новое письмо с прежним файлом остаётся новым источником условий; снимок XLSX при этом дедуплицируется нормализатором по байтам.

Нормализатор использует отдельное состояние `price-updates/current.json` для **последнего разобранного**, а не одобренного прайса. Изменения там не означают подтверждение актуальности, цены магазина или публикацию. Письма обрабатываются по времени доставки Gmail от старых к новым, но время доставки не доказывает дату действия прайса. Подробнее: [версии прайсов](SVAROG-PRICE-UPDATES.md).

## Доверие и безопасность

Любой результат содержит `requires_review=true` и `catalog_changed=false`. Даже знакомый From не получает `sender_approved`. `Authentication-Results` из EML считается непроверенным текстом заголовка; никакие SPF/DKIM/DMARC pass из письма не открывают применение. Выявленная пересылка отмечается `forwarded=true`; отсутствие маркера означает неизвестность, а не доказанное отсутствие пересылки.

Старый `svarog-mail-policy.json` v1 и preflight с прежним контактом сохранены. Новый мост не использует их как разрешение действующего менеджера. Неизвестное или переадресованное письмо может быть разобрано только в частный проект проверки.

Ограничения:

- Оригинал EML — до 35 MiB; до пяти вложений, каждое до 5 MiB; MIME — до 100 частей и глубины 20.
- Вложенное письмо EML не раскрывается: сохраняется исходный оригинал и требуется ручная проверка.
- Небезопасное имя, неподдержанный тип или архив не передаётся нормализатору; байты остаются внутри оригинала, извлечённые допустимого размера — под хешем с расширением `.bin`.
- Формулы и внешние ссылки не исполняются; нормализатор не использует кэш формул как цену.
- Пять страниц Gmail по 100 сообщений — жёсткий предел прохода. Превышение даёт `POLL_LIMIT_REVIEW` до обработки. Не продвигать `--since`, чтобы скрыть непрочитанный остаток.
- Все HTTP endpoints закреплены на Google, редиректы запрещены, таймаут 30 секунд. API ящика вызывается только GET; единственный POST — получение access token на OAuth endpoint.
- Секреты читаются только из отдельного regular file владельца процесса без прав группы/остальных; symlink отклоняется. Секреты не передаются аргументами CLI и не печатаются.
- Частное состояние требует режим 0700, файлы — 0600. Никаких материалов в Git, Docker context или публичной папке.
- Между обработчиками действует один неблокирующий `flock`. Публикация файлов атомарна; оригиналы и квитанции не переписываются.

Для одного Gmail message ID изменившийся SHA оригинала даёт `conflict`; оба оригинала сохраняются. Claim без итоговой квитанции даёт `interrupted`, без повторного запуска парсера. Ошибка нормализации записывается без текста исключения, последующие повторы её не воспроизводят. Для восстановления сначала сверяют claim, исходные SHA и существующие квитанции нормализатора; удалять их ради повторного запуска нельзя. Исправленный парсер и новое производное извлечение требуют отдельного рассмотрения.

## Локальный запуск без OAuth

Этот режим принимает настоящий экспорт письма, но не присваивает ему выдуманный Gmail ID:

```bash
python3 -B ops/suppliers/svarog_mail_bridge.py \
  --state /private/svarog-mail-review \
  ingest-eml --eml /private/original.eml
```

Для сохранения без нормализатора добавить `--save-only`. Такой первый приём остаётся сохранённым результатом; обычный повтор не обходит дедупликацию ради последующей нормализации.

Вывод CLI содержит только статус, количества и коды. Имена, отправители, цены, пути вложений, токены и произвольные ошибки в stdout не выводятся. Частная квитанция содержит происхождение. `prepared` означает готовый частный результат приёма, не применённый импорт; список `normalization` показывает исход обработки каждого вложения. `polled_with_review_errors` возвращает exit code 2.

## Подключение самостоятельного Gmail

Нужно **отдельное согласие владельца Google-аккаунта в браузере** для собственного приложения магазина:

1. Создать или выбрать принадлежащий владельцу Google Cloud OAuth client, включить Gmail API и настроить consent screen.
2. Получить offline grant исключительно для `https://www.googleapis.com/auth/gmail.readonly`. Токены ChatGPT/Codex не копировать. Refresh token не присылать в чат.
3. Разместить отдельный файл на сервере вне Git, например `ops/.secrets/suppliers/svarog-gmail.json`, права 0600, каталог 0700. Формат ниже показан только с заполнителями.
4. Запустить один ручной проход и проверить реальное доставленное письмо/вложение, правильный ящик, SHA, private receipt и повтор без повторного разбора.
5. Только после успешного прохода подготовить закреплённый на commit runner и установить расписание.

```json
{
  "version": 1,
  "mailbox": "bkush7430@gmail.com",
  "client_id": "OWN_GOOGLE_CLIENT_ID",
  "client_secret": "OWN_GOOGLE_CLIENT_SECRET",
  "refresh_token": "OWN_READONLY_REFRESH_TOKEN",
  "scopes": ["https://www.googleapis.com/auth/gmail.readonly"]
}
```

Путь можно передать через `--credentials` или `MW_SVAROG_GMAIL_CREDENTIALS`; содержимое секретов в переменные окружения помещать не требуется. Если Google возвращает scope, мост отклоняет любой более широкий scope. Когда scope в refresh response отсутствует, программа опирается на отдельно выданный readonly grant и декларацию файла; это не самостоятельная проверка всех прав неизвестного токена.

```bash
python3 -B ops/suppliers/svarog_mail_bridge.py \
  --state /private/svarog-mail-review \
  poll --credentials /private/svarog-gmail.json \
  --since 2026-11-11 --opt-in
```

Порядок выдачи offline-доступа описан в [документации Google OAuth](https://developers.google.com/identity/protocols/oauth2/web-server#offline). Используемые операции: [список сообщений](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list), [оригинал сообщения](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get), [проверка аккаунта](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/getProfile).

## Шаблоны расписания

В `ops/suppliers/systemd/` лежат `masterweld-svarog-mail.service.example` и `masterweld-svarog-mail.timer.example`. Они не копировались в systemd и не включались.

Перед установкой заменить `@RUNNER_DIR@`, `@STATE@`, `@CREDENTIALS@`, `@ENABLE_FILE@`. Runner должен содержать проверенные `svarog_mail_bridge.py`, `svarog_price_updates.py`, `svarog_report.py` и шаблон `svarog_report.html` из одного commit; state — прежнее частное состояние, credentials — отдельный секрет. Каталог состояния создать до установки. Контрольный файл включения создаётся только после успешного ручного прохода. Проверить unit через `systemd-analyze --user verify` в реальной среде; ограничения user namespaces могут потребовать отдельного разбора. До этой проверки готовность systemd runtime не заявляется.

Расписание шаблона — раз в час, с задержкой до двух минут. Не создавать дубликат существующей ChatGPT automation. Она может оставаться наблюдателем почты, но самостоятельная обработка магазина должна иметь одну каноническую state-директорию и одного владельца. Шаблоны не меняют существующее резервное копирование.

## Что ещё требуется до обновления магазина

- Отдельный readonly OAuth grant и первое реальное письмо с вложением через настроенную переадресацию.
- Проверка точного отправителя, условий, редакции и происхождения прайса. Полученный общий прайс не является установленной закупочной ценой.
- Штатный actor-bound переход из частного отчёта в document review/import с правами сотрудника, предпросмотром и отдельным подтверждением. Этот мост такого перехода не выполняет.
- Явное правило цены магазина и наличие подходящей версии схемы приложения. Внешние письма не получают прямого write path к товарам.
- Установка проверенного runner/таймера и наблюдение первого самостоятельного прохода. Main/production требуют отдельного release review.

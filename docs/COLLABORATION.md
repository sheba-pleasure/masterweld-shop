# Единая работа с разных компьютеров и агентов
Актуализировано: 29.10.2026.

## Один источник
Репозиторий: https://github.com/sheba-pleasure/masterweld-shop.
dev — общий интеграционный код; main — код для выпуска после проверок.
Компьютер, DevSpace и редактор — рабочие места. История чата не заменяет репозиторий.
Lovable сейчас не требуется. При его возвращении сначала проверить связь и ветку синхронизации, не загружать поверх актуального кода старый снимок.

## Пять шагов для каждой задачи
1. **Прочитать:** AGENTS.md, этот файл, docs/WORKFLOW.md, актуальный раздел roadmap.md и запись задачи в GitHub Issue/PR. Проверить ветку, SHA, remote и git status. Не объявлять серверную копию актуальной без сравнения с GitHub.
2. **Занять задачу:** создать/найти Issue с целью и критерием готовности, записать исполнителя и рабочую ветку task/<номер>-<краткое-имя>. Одна задача — один активный исполнитель; перед передачей явно снять ответственность. Issue — координация, не техническая блокировка.
3. **Работать изолированно:** новая ветка от актуального dev, отдельный clone/worktree для каждого одновременного агента. Не переключать общую рабочую папку под чужим агентом. Не стирать незакоммиченное, не использовать reset --hard/clean/force push. Чужие изменения сначала сохранить отдельно с описанием.
4. **Проверить и сохранить:** проверки по изменению, для кода — npm test и npm run build, серверная сборка/ops-проверки при изменении выпуска. Фиксировать точные команды и результаты, непроведённые проверки обозначать. Только выбранные файлы в commit, затем push ветки и PR в dev. Обновить roadmap при изменении этапа.
5. **Передать:** записать в Issue/PR SHA, сделанное, проверки, незавершённое и следующий конкретный шаг. Незавершённую работу сохранять в task-ветке как WIP, не вливать в dev. После сверки с текущим dev и успешных проверок влить PR без переписывания опубликованной истории. Выпуск — отдельно по docs/WORKFLOW.md.

## Первый запуск на компьютере
Нужны доступ к репозиторию и совместимая с проектом версия Node/npm.
```bash
git clone https://github.com/sheba-pleasure/masterweld-shop.git
cd masterweld-shop
git fetch origin
git switch -c task/123-short-name origin/dev
npm ci
```
123 — номер реальной задачи, short-name — её короткое имя.
Настройки окружения берутся из утверждённого закрытого хранилища. Ключи, .env, прайсы и данные клиентов не коммитить.

Для уже существующего clone сначала git status и git remote -v, затем git fetch origin. Не выполнять pull поверх чужой работы. Если remote отсутствует или папка не является достоверным clone, создать отдельный свежий clone; старую папку не удалять.

## Если есть только GitHub API
Прочитать актуальный head dev и нужные файлы; создать task-ветку от этого SHA.
Отправлять только изменённые файлы, сохраняя остальное дерево.
Перед обновлением ссылки проверить expected head; при изменении ветки заново прочитать и согласовать изменения.
Не заливать полный снимок старой серверной папки. Если проверки выполнить нельзя, открыть draft PR и явно отметить это; не сливать непроверенный код.
Для правки только документации допустим небольшой прямой commit в dev с проверкой ожидаемого SHA, без выпуска.

## Выпуск и откат
dev → PR в main → verify → команда владельца «Выпускай» → точный SHA → проверка выпуска.
Откат приложения: «Откати», порядок в docs/WORKFLOW.md. Это не откат БД или цен.
Никакого автодеплоя от push. Новую публикацию, изменение SEO и живые миграции не включать в обычную синхронизацию кода.

## Что эти правила обеспечивают
Это общий протокол для людей и агентов. Он не создаёт автоматическую синхронизацию, блокировку задач или защиту веток. Конкретный агент должен прочитать инструкции; при отсутствии доступа сообщить об этом и не имитировать проверку.

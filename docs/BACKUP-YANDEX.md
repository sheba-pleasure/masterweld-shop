## Что проверено

Архив заново скачан с Яндекс.Диска. Его размер и SHA-256 совпали с оригиналом. Bridge не возвращает серверные хеши: доказательством служит хеш именно скачанного файла. Проверены все 39 вложенных файлов, отсутствие повторных имён, выхода за папку распаковки и специальных файлов.

Из скачанного комплекта запущен входящий в него проверяющий инструмент. Создан новый временный PostgreSQL без сети и опубликованных портов. Совпали исходные поля всех восьми таблиц; прошли pg_dump/pg_restore, перезапуск и миграции до 0020. Исторических уведомлений не возникло, старые Telegram-квитанции сохранены. Временные контейнер и том удалены.

Это проверка восстановления на свежей базе **того же DevSpace-сервера**. Восстановление на другом физическом сервере и полное восстановление хоста после его потери ещё не проверены. Использован уже имеющийся локальный Docker-образ PostgreSQL.

## Порядок восстановления для администратора

1. Скачать архив и файл контрольной суммы из указанной папки Диска в новую закрытую папку вне сайта. Проверить SHA-256 по значению выше.
2. Проверить список вложений перед распаковкой: только обычные файлы с относительными путями, без `..`, ссылок и повторных имён. Распаковать в новую папку с правами 0700; файлам назначить 0600. Не распаковывать поверх проекта или рабочей базы.
3. Прочитать `ВОССТАНОВЛЕНИЕ.txt` и сверить файлы с BACKUP-MANIFEST.json. Для проверки нужны Python 3, Docker и доступный локально образ `postgres:17.6-alpine`; Python-зависимостей для этого проверяющего инструмента нет.
4. Из корня распакованного комплекта выполнить:

```sh
python3 ops/standalone/verify-cloud-snapshot.py ops/.state/production/cloud-export/20261106T085019Z --restore --upgrade
```

5. Проверить в созданном report.json результат, совпадение строк и удаление временных ресурсов. Эта команда восстанавливает только изолированную копию. Для рабочего переноса использовать отдельную проверенную процедуру [CLOUD-TRANSFER.md](CLOUD-TRANSFER.md).

Исходный архив нельзя напрямую запускать публичным магазином: в исторической схеме есть старый прямой INSERT заказов. Миграции в закрытой проверке устраняют этот путь; это не разрешение на рабочий импорт. Технический DEFAULT new у двух старых заказов не делает их новыми обращениями. Решение владельца об их дальнейшей судьбе остаётся открытым. Сохранённые четыре сотрудника также не означают утверждённые рабочие права.

## Что ещё требуется перед запуском

- Сохранить оригиналы фотографий и проверить их восстановление.
- Перед переходом получить свежий снимок и сверить изменения после 08:50:19 UTC.
- Подготовить резервирование действующей самостоятельной БД и необходимых файлов. Расписание, срок хранения и проверка регулярных копий пока не настроены.
- Испытать восстановление на другом чистом сервере с необходимыми зависимостями.

Это не полный backup Supabase/провайдера или сервера: служебные таблицы платформы, роли с паролями, WAL/PITR и система целиком не входят. Общий release-блокер OFFSITE_BACKUP_RESTORE_REQUIRED автоматически не снят: историческая прикладная копия проверена, но полнота и актуальность резервирования рабочего магазина ещё требуют проверки. Исходный Cloud до завершения сверки не удалять и не отключать.

## Оформление без повторного заказа
Миграция 0013 добавляет service-only журнал попыток order_submissions. Идентификатор попытки и SHA-256 проверенных входных данных связывают запрос с окончательным результатом. Заказ, результат и очередь уведомлений сохраняются одной транзакцией. Транзакционная блокировка сериализует одинаковые попытки. Отказы и предложение новой цены тоже сохраняются: параллельные запросы не могут получить противоположные окончательные результаты.

Повтор сначала читает результат и не зависит от последующих цен/наличия/лимита. Другой состав с прежним ID отвергается. После неизвестного ответа сайт сохраняет исходный запрос в sessionStorage этой вкладки, блокирует новое оформление и предлагает «Проверить и завершить заказ». Перезагрузка вкладки сохраняет попытку. При подтверждённой новой цене создаётся новая попытка с новой суммой.

Границы: защита относится к одному ID попытки. Закрытие вкладки/очистка данных браузера, другой браузер или осознанно новая попытка могут потерять связь с прежней. Поэтому неизвестный результат нельзя разрешать очисткой хранилища; сначала повторить проверку или обратиться к администратору. SessionStorage содержит введённые контакты до окончательного результата и не передаётся в журналы/аналитику. Серверный журнал не очищается автоматически.

Проверка администратором: `python3 ops/dev/order-attempt.py <код-попытки>`. Вывод не содержит контактов покупателя. Отсутствие результата пока не доказывает, что запрос не выполняется.

Прямой INSERT shop_orders для service_role отозван: запись идёт через проверенную RPC. Старое приложение после 0013 не сможет оформить заказ в обход защиты. Откат приложения до реализации 0013 означает недоступность оформления; такая версия не подходит для рабочего отката. Отменять REVOKE ради старого приложения нельзя.

## Сотрудники и управление
Единый источник прав — permissions.ts. Обеим продавцам доступна работа с заказами, карточками, существующими фото и наличием; закупочные цены, изменение розничной цены, публикация и управление сотрудниками закрыты.
Новые роли не добавлялись, существующая модель остаётся расширяемой.
Время заказа и журнала отображается с подписью МСК.
Администратору доступен раздел «Доставка уведомлений»: последние десять записей, состояние и переход к заказу. Это просмотр, без кнопки слепой повторной отправки. Неопределённую доставку сначала сверяют с чатом сотрудника.

## Что блокирует рабочий запуск
1. Рабочего Telegram-бота пока нет — подтверждено владельцем. Создание через BotFather выполняет владелец; затем проверяются getMe, отсутствие чужого webhook/polling и независимый секрет.
2. shop.masterweld.ru не разрешается в IPv4 при проверке сервера. Действующие сайты/Caddy/DNS не изменялись.
3. Нет серверной production-конфигурации, независимого маркера базы и проверенного доступа для штатного backup/restore. SQL-коннектор Lovable позволяет ревизию, но не заменяет pg_dump и восстановление.
4. Нужны сверка полной схемы Cloud, резервная копия и её восстановление, репетиция миграций на копии, согласованное окно переключения. Порядок подготовки: существующие 0000–0002 не повторять; сверить 0003–0013, применить только отсутствующие в проверенной последовательности; 0011 не запускать после 0013 без повторного REVOKE INSERT.
5. Production-уведомления всё ещё намеренно запрещены кодом worker. Их включение требует отдельной конфигурации рабочего бота и release review; нельзя просто поставить флаг true.
6. Живой production deploy/rollback не испытан. Синтетические проверки и восстановление DEV не заменяют его.
7. До покупателей проверить реальные контакты, ассортимент, порядок оплаты/получения, документы магазина и готовность сотрудников. Это не выполнено автоматически тестами кода.

Команда `python3 ops/production/preflight.py` — read-only инвентаризация. Она не выдаёт разрешения на выпуск и не заменяет release report. Пример конфигурации: ops/production/shop.env.example. Реальные значения хранятся только в защищённом shop.env.

После «обнови main» заново проверить точный dev SHA, соответствие работающему DEV, CI/сборку, миграции/backup/rollback, бота и готовность покупателей. При любом блокере остановить продвижение main.

Транзакционные блокировки: [PostgreSQL 17](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS).

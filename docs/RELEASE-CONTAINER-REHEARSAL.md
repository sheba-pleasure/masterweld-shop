# Репетиция переключения контейнеров и отката

## Актуальная репетиция — 07.11.2026

Пройдены 16 сценариев, включая отказ запуска несовместимого остановленного предшественника, запрет несовместимого аварийного возврата после неудачного выпуска и после неудачного отката. В обоих случаях подтверждён HTTP 503, поля активного выпуска очищены, уведомления остаются на паузе. Контрольная строка отдельной базы сохранена.

Первый прогон обнаружил, что nginx reload возвращается раньше фактической смены ответа. Теперь release_maintenance ждёт HTTP 503 и при невозможности подтвердить его сообщает об ошибке. Исправление проверено повторным полным прогоном и синтетическими случаями старого HTTP 200 и недоступной паузы.

Отчёт: `ops/.state/release-rehearsal/4d0fc4f2dd78/report.json`. SHA-256: `0577a284431be4e7650858e9cae5ba12ca146734151a7375a977381e020e5564`. passed=true, existingContainersUnchanged=true, temporaryResourcesRemoved=true. Проверялись рабочие файлы ветки codex/production-schema-compatibility поверх c6fa845; точные SHA-256 скриптов записаны в отчёте. Ссылаться только на исходный HEAD как на версию проверенных изменений нельзя.

Также прошли 44 production Python-теста и 112 синтетических проверок выпуска. Пять HTTP-тестов повторены после добавления ожидания 503. Изменения не развёрнуты в рабочем PRO; DEV-приложение остаётся a93c172. [Проверки совместимости и ограничения](PRODUCTION-SCHEMA-COMPATIBILITY.md).

## Предыдущая репетиция — 06.11.2026

06.11.2026 на DevSpace пройдены 12 сценариев с настоящими Docker-контейнерами, nginx, HTTP и текущими release.sh/rollback.sh. Приложение в этих контейнерах — учебный HTTP-сервис. Рабочие БД, Telegram, сайты, Caddy, VPN и SSH не подключались и не переключались. Main не обновлялся.

## Что проверено

1. Ошибка после самого первого переключения оставляет gateway в 503, без активного выпуска и обработчика уведомлений.
2. Первый успешный выпуск подтверждает точный SHA через настоящий nginx после reload.
3. Маршрут backend доходит до отдельного учебного backend и сохраняет Authorization.
4. Второй выпуск сохраняет предыдущий контейнер; право обрабатывать уведомления получает только новая версия.
5. Перезапуск предыдущего контейнера не активирует его обработчик.
6. Откат возвращает прежнюю версию и её обработчик без запросов GitHub.
7. Неверный SHA нового контейнера отвергается до переключения трафика.
8. Неверный SHA через gateway приводит к автоматическому возврату предыдущей версии и её обработчика.
9. Неудачный откат возвращает трафик и право обработки текущему выпуску.
10. Откат способен запустить остановленный предыдущий контейнер и подтвердить его SHA.
11. Занятый release.lock запрещает второй выпуск.
12. Контейнер приложения не может записать разрешение в read-only mount обработчиков.

Учебный HTTP-сервис импортирует настоящий notificationWorkerActive из проекта. Проверки до включения новой версии видят обработчик неактивным. Функция отправки уведомлений, Telegram-транспорт и подключение к БД в образ не включены.

## Изоляция и настройки

Скрипты прежде содержали фиксированные имена и порты. Теперь адреса служебных ресурсов можно передать через окружение; значения по умолчанию остались production:

| Переменная | По умолчанию |
|---|---|
| MW_CONTAINER_PREFIX | mw-shop |
| APP_NETWORK | mw-prod-edge |
| GATEWAY_PORT | 18080 |
| SLOT_A_PORT | 18081 |
| SLOT_B_PORT | 18082 |
| BACKEND_PORT | 18084 |
| MW_PRODUCTION_DB_CONTAINER | mw-prod-db |
| MW_PRODUCTION_DB_NAME | masterweld_production |

Gateway получает имя `<префикс>-gateway`, приложения — `<префикс>-slot-a/b`. Привязка остаётся строго 127.0.0.1: переменная BIND_IP извне её не меняет. Имена проверяются по допустимым символам, порты — на диапазон 1024–65535 и отсутствие совпадений до записи состояния или вызова Docker. Проверка метки production у выбранной сети сохранена. Проверки main/merge/verify, меток образа, окружения приложения и состояния не ослаблены.

Для репетиции инструмент сам выбирает уникальные имена `mw-rehearsal-<id>`, четыре свободных loopback-порта, отдельные образы, отдельный bridge и закрытую папку состояния. Production-сеть не используется. GitHub заменён локальным HTTP-сервером с учебными ответами. Секреты проекта не читаются; токен в фикстуре заведомо вымышленный.

Это обычная выделенная bridge-сеть с публикацией только loopback-портов, не запрет любого исходящего сетевого доступа. Сервис не содержит исходящих запросов. Поведение bridge и публикации портов описано в [документации Docker](https://docs.docker.com/engine/network/drivers/bridge/). Первые две репетиции с internal-сетью на этом хосте не получили опубликованных портов и остановились до переключения; их ресурсы удалены. Применение отдельного bridge не меняло существующие сети.

При ручном использовании альтернативной конфигурации один и тот же набор переменных нужен для gateway, выпуска и отката вместе с отдельными STATE_DIR, SECRETS_ENV и IMAGE_REPO. Для штатного production эти значения переопределять не требуется. Для проверки использовать готовый инструмент ниже; вручную запускать production-скрипты с учебными значениями не нужно.

## Повторный запуск

Из корня чистого checkout после установки зависимостей:

```sh
python3 ops/tests/release-containers.py
```

Нужны Docker и заранее доступные локальные образы node:22-bookworm-slim, nginx:1.27-alpine и postgres:17.6-alpine. Текущая репетиция создаёт отдельную минимальную PostgreSQL-фикстуру без сети для проверки совместимости; существующие базы не читает. Инструмент не скачивает их автоматически. CI получает эти публичные образы отдельным шагом. Esbuild из зависимостей проекта собирает только функцию контроля активности; Docker-сборка фикстуры выполняется без сети.

Отчёт и диагностические логи сохраняются в закрытой `ops/.state/release-rehearsal/<id>/`, вне Git. Временные контейнеры, сеть и теги образов удаляются при завершении, включая отказ проверки. Ошибка очистки делает проверку неуспешной. При аварийном завершении процесса или хоста администратор должен проверить оставшиеся ресурсы по ID из папки отчёта; автоматическая очистка после SIGKILL не гарантируется.

В CI этот сценарий обязателен после синтетических проверок выпуска. Он не выполняет production deploy.

## Что эта репетиция не доказывает

Это проверка механики выпуска и отката, а не полного production-магазина. Здесь не запускались production runtime, проверка настоящего маркера БД, настоящие боты, оформление заказа или рассылка. Учебные ответы GitHub не подтверждают разрешение на реальный выпуск. Не испытывались внешний SSH-приёмник, GitHub → сервер, production-домен/HTTPS и переключение webhook.

Остаются репетиция с окончательной конфигурацией приложения, перенос данных и медиа, внешний выпуск/откат и рабочая приёмка. Готовность main определяется отдельным release review после команды владельца «обнови main». Общая цель остаётся открытой.

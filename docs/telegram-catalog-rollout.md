# Этап C1: панель управления каталогом в Telegram — порядок развёртывания и откат

Интернет-магазин «Мастер Сварщик». Документ описывает безопасный rollout
панели управления каталогом в Telegram-боте: чтение, поиск, карточки и
двухшаговые изменения цены/наличия (preview → confirm).

## Что реализовано в коде (C1)

### Чтение (работает сразу, миграция не нужна)

- Команды в личном чате сотрудника с ботом:
  - `/start`, `/menu` — меню с inline-кнопками;
  - `/catalog` — каталог с пагинацией (по 10);
  - `/find <артикул или модель>` — поиск по названию/SKU/бренду с нормализацией
    (регистр, ё→е, тире, пробелы), до 10 результатов на страницу;
  - `/product <артикул или модель>` — карточка товара; неоднозначный/дублирующийся
    SKU показывается списком, произвольный товар не выбирается;
  - `/summary` — фактическая сводка: published / draft / hidden,
    «отмечено в наличии» / «под заказ» (без обещаний физических остатков).
- Inline-кнопки: «🗂 Каталог», «🔍 Найти товар», «📝 Черновики», «🚚 Под заказ»,
  «📊 Сводка», список «💰 Цена снижена» (только `old_price > price`).
- Карточка товара: UUID, SKU, наименование, цена, скидка (только если
  `old_price > price`), бренд, статус, флаг наличия, категория, число фото.
  Закупочные цены (`product_costs`) не читаются и не показываются.
- Приватность: все служебные данные и операции — только в личном чате
  (`chat.type === "private"` и `chat.id === from.id === staff.telegram_id`). RBAC проверяется на каждом
  callback. Персональные данные заказов — как в этапе A (только `manage_orders`
  и только в личном чате).

### Безопасность всей админки — код 25.10.2026

- Единый gate в `handleUpdate` ДО чтения staff и callback-обработки: все команды
  (включая `/start`, `/menu`, неизвестные), медиа, редактор, каталог, заказы, B2B,
  сотрудники, журнал и elevated — только private. Отсутствующий `chat.type`,
  callback без message, несовпадение реального sender/chat/staff и смешанный update
  отклоняются. Callback не заимствует actor из `update.message`.
- Групповой callback получает только нейтральный `answerCallbackQuery`, команда —
  «Нет доступа». Ни staff-чтения, ни служебного меню, ни изменений из группы.
- «Сотрудники» и «Журнал»: RBAC → успешная запись аудита → чтение → раскрытие.
  Ошибка аудита/чтения закрывает выдачу; provider error в ответ не попадает.
- Elevated переведён на `bot_toggle_elevated`: только активный директор, сверка
  старого elevated, UPDATE + аудит одной транзакцией. **0010 НЕ применена**;
  без RPC переключение заблокировано, роли и права продавцов не расширены.
- Подробные ошибки БД из handler больше не логируются. Доставка `tg()` теперь
  явно отвергает HTTP/API/сетевые ошибки. Claim webhook после ошибки сохраняется
  для предотвращения слепого повтора изменений; гарантированной доставки/outbox
  пока нет — ограничения и ручная сверка описаны в `docs/order-rollout.md`.
- 63 новые mock-проверки доступа/аудита/RPC/доставки прошли (exit 0).
  Реальные SQL-конкурентность и Telegram E2E не выполнялись; это не production-ready.

### Двухшаговые изменения: `/price` и `/stock`

- `/price <SKU или модель> <цена>` — требует право `edit_prices`
  (продавец не может; директор и админ могут).
- `/stock <SKU или модель> <есть|под_заказ>` — требует право `edit_stock`.
- Парсер цены: до 10 000 000 ₽, до 2 знаков после запятой; 0, отрицательные,
  «1.234» (3 знака) и мусор отклоняются.
- Неоднозначный SKU (дубли) или несколько совпадений — список выбора конкретного
  UUID; ничего не найдено — отказ. Произвольный товар никогда не изменяется.
- Предпросмотр «было → станет» с кнопками «✅ Подтвердить» / «⬅️ Отмена».
- `stock_qty` не изменяется и не выводится — количество не придумывается.
- `slug` и `source_url` не изменяются никогда.

### ⚠️ Изменения цены/наличия заблокированы до применения миграции 0005

Таблица `pending_actions` (файл `docs/migrations/0005_bot_pending_actions.sql` —
материал для ревизии; применение — через инструмент миграций Lovable)
хранит снимок «было → станет», TTL (15 минут), владельца действия, момент
завершения (`consumed_at`) и итог (`outcome`: `applied` / `canceled`).
Отмена НИКОГДА не считается применением. Пока таблицы нет:

- чтение (каталог, поиск, карточки, сводка) работает полностью;
- изменяющие команды показывают предпросмотр, но вместо кнопки подтверждения
  выводят «⚠️ Функция ещё не активирована: требуется обновление базы» —
  ложное подтверждение невозможно.

Защита после применения миграции:

- TTL: подтверждение после `expires_at` отклоняется;
- anti-replay: применение/отмена помечают `consumed_at` и `outcome` атомарно
  (в 0006 — внутри одной транзакции вместе с UPDATE товара); повторный клик
  получает отказ;
- откат: только для `outcome = 'applied'` и только если текущее значение
  ТОЧНО равно `after_value` исходного действия; если поле изменили ещё раз
  после применения (100→200→300), откат запрещён с сообщением о конфликте —
  молчаливое «вернуть как было» невозможно;
- владелец: подтвердить может только сотрудник, создавший предпросмотр;
- сравнение старого значения: перед UPDATE текущее значение товара сверяется
  со снимком `before_value`; при расхождении (параллельное изменение) —
  отказ «данные изменились»;
- конкурентность: UPDATE товара дополнительно условный по старому значению
  (`WHERE price = было` / `WHERE in_stock = было`);
- аудит: `staff_audit_log` получает запись `catalog_price` / `catalog_stock` /
  `catalog_*_conflict` / `catalog_cancel` с actor, before и after.

## Порядок развёртывания (строго по шагам)

1. **Ревизия** файла `docs/migrations/0005_bot_pending_actions.sql`.
   Миграция additive: новая таблица, только `service_role`, без публичных политик.
2. **Применить 0005** через инструмент миграций Lovable (он ведёт журнал сам;
   файл в `docs/migrations/` — материал для ревизии, а не автозапуск).
3. **Развернуть код** бота.
4. **Проверка end-to-end** в личном чате:
   - `/find <SKU>` — поиск, пагинация, карточка;
   - `/price <SKU> <цена>` — предпросмотр, «Подтвердить» → цена изменена,
     аудит записан; повторный клик по старой кнопке — отказ (replay);
   - открыть предпросмотр, изменить товар другим способом, подтвердить —
     отказ «данные изменились»;
   - `/stock <SKU> под_заказ` — аналогично;
   - продавец: `/price` — «недостаточно прав»; `/stock` — разрешено;
   - директор в простом режиме: `/price` разрешено (`edit_prices` есть).

## Откат

- **Код**: откатить деплой — бот вернётся к чтению; `pending_actions` просто
  перестанет использоваться.
- **Миграция 0005**: таблица ни на что не влияет, кроме бота; удаление
  (`DROP TABLE public.pending_actions`) вернёт состояние до C1. До удаления
  убедиться, что неприменённых/неподтверждённых предпросмотров не ждут.

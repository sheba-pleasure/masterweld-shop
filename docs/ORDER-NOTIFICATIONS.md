# Уведомления о новых заказах

## Сотруднику

Новый заказ приходит в личный чат с @testmw639bot: номер, сумма, кнопка «Открыть заказ». Нажмите её, проверьте состав и выберите «→ в обработке». Нижнее меню остаётся доступным. Телефон, имя покупателя и закупочные цены в уведомление не включаются.

Получатели — сотрудники, активные при оформлении заказа и имеющие manage_orders непосредственно перед отправкой. Сейчас право есть у администратора, директора и продавца; единственный источник правил — src/lib/bot/permissions.ts. Сотрудник должен ранее запустить бота в личном чате. Новым сотрудникам старые заказы автоматически не рассылаются.

## Администратору

Заказ и строки очереди создаются одной транзакцией через триггер 0012. Сбой Telegram не отменяет сохранённый заказ. Приложение проверяет очередь каждые 2 секунды, обрабатывая до пяти записей за проход. При очереди/ограничениях Telegram доставка может занять больше времени.

В DEV включено ORDER_NOTIFICATIONS_ENABLED=true в защищённом app.env. Worker запускается внутри того же контейнера после проверок среды, базы и бота. Подготовлен отдельный production-путь только для @masterweldermanagerbot; рабочая рассылка пока выключена. Наличие кода не означает рабочего запуска.

Проверка состояния: `python3 ops/dev/notification-status.py`. Команда показывает количества и проблемные записи; код 1 означает необходимость проверки. Имена/телефоны покупателей не выводятся.

- sent: Telegram вернул message_id, результат сохранён.
- skipped: сотрудник больше не имеет доступа либо заказ уже не новый.
- pending: ожидает отправки или безопасного повтора.
- failed: явный отказ Telegram, недоступный чат или исчерпан лимит попыток; проверьте сотрудника и его запуск бота.
- uncertain: результат неизвестен. Сначала проверьте чат и заказ вручную. Автоматическая повторная отправка запрещена.
- sending: запись захвачена обработчиком; после аварии через пять минут переходит в uncertain.

Не очищайте очередь ради повторной отправки и не меняйте state вручную без проверки чата. Заказы всегда доступны через «Заказы», даже если уведомление не дошло.

## Защита от дублей и границы

Первичный ключ (order_id, staff_telegram_id) исключает вторую запись для того же заказа и сотрудника. FOR UPDATE SKIP LOCKED и claim_token исключают одновременную отправку одной строки несколькими обработчиками. Перезапуск не повторяет sent. Невыясненная отправка после таймаута/5xx/потери подтверждения БД не повторяется: sendMessage не предоставляет ключ идемпотентности. Это предотвращает автоматические дубли ценой ручной проверки неопределённых доставок; гарантии «каждый заказ доставится ровно один раз при любом сбое» нет.

Безопасные повторы до трёх попыток разрешены только до вызова Telegram при ошибке чтения либо при явном 429 с корректным retry_after. Пауза не короче retry_after и 60 секунд. Неизвестная роль, отрицательный chat ID и отключённый сотрудник не получают уведомление. Кнопка карточки повторно проходит обычную проверку сотрудника и личного чата.

Повторный запрос покупателя, создающий другой UUID заказа, — отдельный заказ. Эта задача устраняет дубли уведомления одного заказа, а не объединяет разные заказы.

Миграция 0012 сначала применена к masterweld_dev после резервной копии; она также входит в схему новой пустой самостоятельной production-БД (0000–0013). Старый Cloud не мигрировался. Она не рассылает исторические заказы. При откате приложения очередь остаётся в БД. При отключении worker новые заказы продолжают попадать в pending; после включения обрабатываются только ещё новые заказы.

## Рабочая среда: подготовлено, пока выключено

Рабочая конфигурация `shop.env.candidate` остаётся с ORDER_NOTIFICATIONS_ENABLED=false. Пустая production-база не рассылает уведомления; рабочий webhook сотрудников пока обслуживается прежним backend. Включение требует отдельной проверки выпуска после команды владельца «обнови main».

Перед отправкой production проверяет:
1. APP_ENV=production, самостоятельную БД и её instance ID, неизменяемые параметры сборки.
2. Рабочего служебного бота @masterweldermanagerbot / 8861999166 через getMe; DEV и покупательский бот не подходят.
3. Точный webhook https://shop.masterweld.ru/api/public/telegram/webhook через getWebhookInfo при запуске. Если бот ещё подключён к старому backend, приложение с включённой рассылкой не запускается.
4. Разрешение конкретному slot и SHA в read-only файле /run/mw-workers/active.json перед каждым захватом очереди. Ошибка чтения, отсутствующий или некорректный файл означает паузу.

Сначала рабочий сайт запускается с выключенными уведомлениями. Затем в согласованное окно подключаются webhook, проверяются сотрудники, права и один заказ. Уведомления включаются в следующем проверенном выпуске; конфигурация самого контейнера при простом docker restart не перечитывается. Не обходить проверку webhook и не подменять SHA ради включения.

### Обновление и откат

ops/release.sh передаёт контейнеру его SHA и slot; файл env их не подменяет. Из состояния монтируется только каталог workers, без разрешений выпуска и секретов. Каталог и файл принадлежат оператору, запись для группы/других и symlink запрещены. Корневой ops/.state также не должен быть доступен группе/другим на запись.

Новый контейнер не берёт очередь до проверки сайта. Перед переключением трафика очередь ставится на паузу; после успешной проверки, записи состояния и журнала разрешение получает новая версия. Старый контейнер остаётся доступным для отката, но новые задания не захватывает. При неудачной проверке и успешном возврате трафика разрешение возвращается прежней версии. Офлайн-откат действует аналогично, без обращения к GitHub.

Уже начатый захват/отправка может завершиться после переключения. Каждая запись защищена атомарным claim и claim_token; она не возвращается в pending ради выпуска. Это не мгновенная отмена сетевого запроса и не обещание доставки ровно один раз.

При аварийном прерывании скрипта после паузы уведомления могут остаться на паузе. Заказы сохраняются и доступны сотрудникам. Оператор сверяет active_slot/active_sha, метки контейнера и работоспособность сайта; затем выполняет проверенный выпуск или откат. Не редактировать очередь или active.json ради повтора неизвестной отправки. При откате на контейнер с ORDER_NOTIFICATIONS_ENABLED=false рассылка останется выключенной, даже если этот slot активен.
